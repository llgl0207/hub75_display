### 🤖 AI

建议把 **MIZAR R7（XC7Z020）**按“PS 负责应用与联网，PL 负责实时显示与扫描”的方式分工。Zynq-7000 的 PS 是双核 Cortex-A9，可运行嵌入式 Linux；PL 用来实现 HUB75 的确定时序和像素输出。关键是让无线、渲染和屏幕扫描互相解耦，避免 Linux 调度抖动影响显示。

```text
手机 / 上位机
      │ Wi-Fi / Ethernet
      ▼
PS：联网、控制协议、配置、素材管理、状态监控
      │ AXI-Lite 控制 + DDR 帧缓冲
      ▼
PL：帧缓冲读取 → 像素格式/亮度处理 → HUB75 行扫描与时序
      │
      ▼
HUB75 面板
```

**PS 侧软件**

- 先用 Linux 做原型，负责 Wi-Fi、Web 配置页或 TCP/UDP 控制接口、画面素材管理、音频/数据采集，以及系统状态和错误日志。
- 将“显示内容”抽象成统一场景或帧缓冲接口。无线控制只提交参数或素材，不直接操作 GPIO、也不承担逐行刷新。
- 做体积显示器时，可以把音频分析与画面表现分开：音频线程输出音量包络、频段能量等特征；渲染线程根据特征生成画面。
- Linux 下可先用 `/dev/fb`、DRM 或自定义 DMA 驱动管理帧缓冲；具体选哪种取决于系统镜像和显示分辨率。

**PL 侧硬件**

- HUB75 扫描器使用独立时钟域和状态机，负责行地址、RGB 数据移位、CLK、LAT、OE，以及扫描行切换。
- 显示数据通过 AXI HP 端口从 DDR 读取；AXI-Lite 用于设置分辨率、扫描方式、亮度、帧地址等控制参数。
- 用双缓冲或多缓冲：PS 写非显示缓冲，PL 只读当前缓冲；在垂直消隐或帧边界切换缓冲地址，避免撕裂。
- 若面板为多扫描方式、需要较高刷新率或灰度位平面，PL 中再做位平面调度、PWM/BCM 和亮度控制。不要一开始就把完整图形渲染塞进 PL。

**帧缓冲与性能**

先确认面板的实际参数：宽高、级联数量、扫描比（如 1/8、1/16）、颜色深度、目标刷新率，以及面板是否需要特定的 HUB75E 行地址/额外控制信号。仅凭 XC7Z020 型号无法确定帧缓冲带宽和扫描实现。

以 128×64、RGB888、60 fps 粗略估算，单个紧凑帧缓冲约 **24 KiB**，仅按每帧一次读取约 **1.5 MB/s**；但若 PL 按扫描周期重复读取整帧，实际 DDR 流量会更高。因此建议 PL 侧加 FIFO/行缓冲，并根据位平面和刷新率测量带宽与时序裕量。面板若要求高刷新率或更多灰度位，先做时序与带宽预算，再定缓冲格式。

**无线控制边界**

无线链路适合发送场景、亮度、颜色、模式、参数和素材；实时画面最好由 PS 本地生成，或按完整帧/压缩素材发送。避免通过无线逐像素推送并把它当成可靠的实时显示总线。控制协议可从 HTTP/REST 或 WebSocket 开始，并提供连接状态、当前模式、亮度和错误状态。

**推荐开发顺序**

1. 查清 MIZAR R7 的启动方式、DDR、可用网络接口和现有 Linux/裸机支持，再确认面板规格与引脚电平。
2. 用 PL 做单色 HUB75 扫描，先验证行地址、锁存、OE、时钟极性和刷新稳定性。
3. 扩展成 RGB 与目标灰度；加入行 FIFO、双缓冲和帧边界切换。
4. PS 先写固定测试图到缓冲区，再验证 AXI/DMA 读屏与帧切换。
5. 加入渲染与音量分析，最后接无线控制和配置界面。
6. 用逻辑分析仪测 HUB75 时序；用测试图检查撕裂、鬼影、亮度均匀性和长时间稳定性。

如果这是**单块或少量面板、主要显示本地生成的动画**，建议先采用 PS 端 Linux 渲染、PL 端扫描的混合架构；如果目标是低延迟、强实时或无 Linux 启动环境，再考虑裸机/RTOS。下一步最需要确认的是面板尺寸、扫描比、级联数量和无线模块/网络接口。

从零开始、又要尽快看到整屏效果，建议第一阶段只做一件事：**让 PL 用固定测试图稳定驱动面板**。先不接 Linux、无线、音频或动态渲染。HUB75 的难点主要是扫描时序、面板接线和电气兼容，不是先把整个系统架构做复杂。

## 开发路径

### 1. 先确认硬件，避免对着错误时序调试

整理面板和开发板资料，至少确认：

- 面板尺寸、扫描比，例如 64×32、1/16 扫描
- HUB75 接口类型和行地址信号：A/B/C/D，或额外的 E
- 面板供电电压、电流，以及信号输入电平要求
- MIZAR R7 上哪些 PL 引脚能接到 HUB75 转接板
- 面板是否需要专用驱动/缓冲芯片或电平转换

不要默认面板能直接接 FPGA。**面板电源通常需要独立供电，电源地要与开发板共地；信号电平和驱动能力需按板卡与面板资料确认。**先用转接板或合适的缓冲/电平转换电路，不要让面板电源从 FPGA IO 供电。

### 2. 让 PL 先输出静态控制时序

用 Vivado 建立最小工程，先完成时钟、复位和引脚约束，验证一个扫描行的循环：

1. 设置行地址。
2. 关闭输出 OE。
3. 移位输出 RGB 数据，同时产生 CLK。
4. 产生 LAT 锁存。
5. 打开 OE 显示一段时间。
6. 切换到下一行。

这一阶段不要先追求灰度或高刷新率。先让每行有正确的数据、行地址和锁存关系。用逻辑分析仪或示波器观察 CLK、LAT、OE、行地址信号，确认极性和相对时序。

### 3. 用可识别的测试图逐项排错

按这个顺序换图，避免同时改很多变量：

- 全黑：检查是否误点亮、OE 极性是否正确
- 全红、全绿、全蓝：检查 RGB 线序与颜色通道
- 单列竖线、单行横线：检查移位方向、像素数和行地址
- 红绿蓝条纹或棋盘格：检查位序、锁存和数据稳定时间
- 低亮度渐变：最后再加入 PWM 或位平面灰度

如果图像呈现规律性错位，优先检查扫描比、移位方向、行地址编码、RGB 通道顺序和面板接口类型；如果有鬼影或闪烁，检查 OE 关断时机、LAT 脉冲和行切换间隔。

### 4. 再实现完整的行扫描与灰度

静态单色通过后，依次加入：

- 所有扫描行循环
- RGB 输出
- 亮度控制
- PWM 或二进制码调制（BCM）灰度
- 帧率、亮度与位深的取舍

先选一个保守目标，例如低位深、稳定刷新，再逐步提高。不要一开始就追求 24-bit 色深；HUB75 的扫描占空比、面板驱动芯片和时序预算都会限制实际效果。

### 5. 最后接入 PS、渲染和无线

PL 独立稳定后，再从固定测试图过渡到可写帧缓冲：

- PS 通过 AXI/DMA 写入 DDR 帧缓冲。
- PL 读取显示缓冲，最好先用行缓冲/FIFO。
- 使用双缓冲，在帧边界切换显示地址，避免撕裂。
- 最后接入渲染、音量分析和无线控制；无线只传模式、参数和素材，不承担 HUB75 的实时扫描。

### 🤖 AI

既然 HUB75 的电气时序已由 H7 实测并定下，FPGA 阶段就把这些参数当作接口契约。开发重点是建立一个**可综合、可仿真、可上板验证、可回归**的流程，先验证 PL 输出，再逐步接入帧缓冲和 PS。

## 推荐流程

### 1. 把 H7 测量结果整理成时序契约

先写一张表，记录系统时钟频率，以及每个信号的：

- 空闲电平、有效电平和输出时刻
- CLK 周期、高低电平宽度
- RGB 相对 CLK 的建立/保持时间
- 行地址切换时刻
- LAT 脉宽及其相对 CLK、OE 的位置
- OE 的有效电平、消隐区间
- 一行移位像素数、扫描行数、刷新目标
- 上电复位后的安全输出状态

这些值要落成 HDL 参数或配置常量，避免散落在状态机代码中。需要区分**面板要求的信号时序**和**FPGA 内部状态机的时钟周期数**，后者要由系统时钟换算。例如系统时钟为 100 MHz，周期是 10 ns；面板要求的 40 ns 脉宽至少对应 4 个时钟周期。

### 2. 建立最小 RTL 工程

按功能拆成简单模块，不要一开始引入完整 SoC：

- `hub75_timing`：行扫描状态机，控制移位、锁存、消隐和行地址
- `pattern_gen`：生成固定测试数据
- `hub75_top`：时钟、复位、模块连接和顶层引脚
- `tb_hub75_timing`：时序检查与扫描计数测试

先用计数器和固定图案作为数据源。此时目标是验证状态机输出符合契约，不涉及 PS、AXI、DDR 或渲染。

### 3. 在仿真中先验收时序，再上板

写 testbench 驱动时钟和复位，至少检查：

- 一个扫描行输出了正确数量的 CLK
- RGB 在规定的 CLK 边沿前后保持稳定
- LAT、OE 和行地址的时序关系正确
- 行地址遍历顺序正确，最后一行之后回到首行
- 复位与启动过程中 OE 保持在安全状态
- 行周期、帧周期符合计算值

建议使用 SystemVerilog assertion，或在 testbench 里写明确的计数和边沿检查。对已知硬件时序值做参数化后，仿真可以直接检查最短脉宽、建立/保持时间和周期，而不是仅靠肉眼看波形。

### 4. 固定测试图上板

仿真通过后，生成 bitstream，下载到 PL。测试图按可诊断性排列，例如全色、竖条、横条和单像素移动。用 H7 或逻辑分析仪再次观测 FPGA 引脚输出，与时序契约逐项对照。若波形不符，回到 RTL/约束修正；若波形符合但画面不符，检查数据顺序、行地址映射和面板配置。

### 5. 加入帧缓冲接口，但先隔离显示扫描

固定图案稳定后，再定义显示数据接口，例如：

```text
像素请求：x、y、valid
像素响应：RGB、valid
```

随后用片上 ROM 或 BRAM 代替固定图案，验证扫描器能正确取像素。接下来再把数据源替换为 DDR 帧缓冲读取逻辑，PL 显示扫描时序本身尽量不改。

接 PS/DDR 时再处理 AXI/DMA、FIFO、水位和帧边界切换。用双缓冲避免读写同一帧导致撕裂；PS 只更新待显示缓冲地址，PL 在完整帧边界切换。

## Vivado 的日常迭代闭环

每轮只做一个改动，按固定步骤走：

1. 编辑 RTL 和仿真测试。
2. 跑行为仿真，检查断言与关键波形。
3. 跑综合、实现和时序分析，确认无未约束路径、无负 slack。
4. 检查 I/O 引脚和电气标准约束，避免顶层端口遗漏或绑定错误。
5. 下载 bitstream，上板验证图案和波形。
6. 保存通过版本、测试结果和对应参数。

工程初期尤其要把 **时钟约束（XDC）**写对：声明板上实际输入时钟，所有输出引脚指定正确封装管脚和 I/O 标准。内部计数器产生的时钟尽量不要当作新时钟域使用；HUB75 输出时钟应作为普通输出由同步逻辑产生，避免无必要的派生时钟域。

## 后续里程碑

1. 仿真通过的单行、固定颜色时序。
2. 上板稳定扫描全屏固定测试图。
3. 扫描所有行并完成 RGB 与目标灰度。
4. 用 BRAM/ROM 图案验证像素索引和行缓冲。
5. 通过 AXI/DMA 读取 DDR 帧缓冲。
6. 接入 PS 渲染、音量数据和无线控制。

就你当前阶段，建议先完成第 1 项：把 H7 测量表转成参数，并写一个能自动检查 CLK 数量、LAT/OE 关系和行周期的 testbench。这样后续改动可以靠回归仿真保证时序没有被破坏，而不是每次都从波形和面板现象重新猜。

## 第一版工程的边界

固定使用 `OE=1` 表示移位和锁存期间消隐；一行按 **移位数据 → 更新 A~E 地址 → LAT 锁存 → 显示** 的顺序执行。首版可使用约定里建议的像素时钟范围，并选择保守值验证；刷新目标先按整个扫描帧达到约 120 Hz 估算，再结合你实际的 FPGA 系统时钟换算状态机周期数。[时序约定](<HUB75_FPGA迁移参数与参考时序.md>)里某些绝对时间是由 H7 代码推导或估算的，工程参数应将它们显式化，避免把估算误当成已由 FPGA 引脚测得的保证值。

## 注意 `FRAME_HZ` 的含义

`FRAME_HZ` 是用于计算行周期的目标参数：

```verilog

```

由于这里使用整数计数，实际帧率是：


例如 `FRAME_HZ=120` 时：

```text

          ≈ 120.008 Hz
```

因此最终应以示波器或逻辑分析仪测量完整帧周期为准，而不是只看参数值。

因为它每完成一帧只翻转一次，所以：

```text
刷新率 = 1 / (frame_mark 周期 / 2)
```

例如测得 `frame_mark` 周期为 1.667 ms：

```text
刷新率 = 2 / 1.667 ms ≈ 1200 Hz
```

保持：


也就是每帧移动一个像素。这样流水速度可以直接反映实际刷新率。

依次测试：

4. 屏幕是否正常显示；
5. 亮度是否明显下降；
6. 是否有鬼影、错行和闪烁。

定义两个结果：

```text

    状态机仍能合法运行、时序满足、实现通过的最高值。

    实测无明显鬼影、错行、亮度异常和闪烁的最高值。
```

这两个数很可能不同。例如：

```text

面板最高稳定刷新率：可能是 600 Hz 或 800 Hz
```

## 测最高像素 CLK 的推荐流程

### 第一步：固定场刷新率，只测 CLK 上限

先固定：

```verilog
.FRAME_HZ(120)
```

然后逐步修改：

```verilog
.PIXEL_CLK_HZ(5_000_000)
.PIXEL_CLK_HZ(8_000_000)
.PIXEL_CLK_HZ(10_000_000)
.PIXEL_CLK_HZ(12_000_000)
.PIXEL_CLK_HZ(15_000_000)
.PIXEL_CLK_HZ(20_000_000)
```

每次使用黑白 1 像素竖条测试图，观察是否出现：

- 随机亮点
- 颜色错乱
- 左右错位
- 竖条不均匀
- 局部区域异常
- 亮度突然下降

第一个出现异常的频率记为：

```text
面板可接受 CLK 的边界
```

然后退回一个档位，并增加长时间测试，例如运行 10 分钟。

不过需要注意，当前 `50 MHz` 系统时钟下，状态机每个像素的 CLK 高、低相位至少由系统时钟粒度控制。`PIXEL_CLK_HZ=20 MHz` 时，每半周期只有约 1.25 个系统时钟，实际会被整数分频限制，不能精确产生 20 MHz。

当前代码：

```verilog
HALF_DIV = ceil(CLK_HZ / (2 * PIXEL_CLK_HZ))
```

因此实际像素时钟应按下面公式计算：

```text
实际像素 CLK = 50 MHz / (2 × HALF_DIV)
```

例如：

| 目标 `PIXEL_CLK_HZ` | `HALF_DIV` | 实际 `hub_clk` |
|---:|---:|---:|
| 5 MHz | 5 | 5 MHz |
| 8 MHz | 4 | 6.25 MHz |
| 10 MHz | 3 | 8.33 MHz |
| 12 MHz | 3 | 8.33 MHz |
| 20 MHz | 2 | 12.5 MHz |
| 25 MHz | 1 | 25 MHz |

所以当前 50 MHz 主时钟下，建议测试实际可生成的档位，而不是任意目标值：

```text
5 MHz
6.25 MHz
8.33 MHz
12.5 MHz
25 MHz
```

其中 25 MHz 已经是“每个高、低相位各一个 50 MHz 时钟”的极限，但这通常不代表面板能可靠接受。面板是否能接收还取决于电平转换、走线和 HUB75 驱动芯片。

## 第二步：测最高场刷新率

确定一个稳定的像素 CLK 后，再让每个扫描行尽可能短。

对于一行：

```text
Trow = Tshift + Taddr_setup + TLAT + Tblank + Ton
```

其中：

```text
Tshift = 128 / 实际 hub_clk
```

整屏是 32 个扫描地址：

```text
Tframe = 32 × Trow
Fframe = 1 / Tframe
```

例如 `hub_clk=5 MHz`：

```text
Tshift = 128 / 5 MHz = 25.6 us
```

在 50 MHz 系统时钟下，至少需要约：

```text
128 × 2 × 5 = 1280 个系统时钟
```

再加上地址和 LAT 的余量，理论场刷新率约为：

```text
50 MHz / (约 1300 × 32)
≈ 1200 Hz
```

这只是 RTL 的理论上限。实际面板还需要保留 OE 点亮时间，否则虽然扫描频率很高，但屏幕会非常暗。

建议增加一种“最高速扫描模式”，让每行周期直接由最小开销决定，而不是通过 `FRAME_HZ` 反推：

```verilog
parameter integer ROW_TICKS_OVERRIDE = 0;
```

逻辑上：

```verilog
if (ROW_TICKS_OVERRIDE != 0)
    ROW_TICKS = ROW_TICKS_OVERRIDE;
else
    ROW_TICKS = CLK_HZ / (FRAME_HZ * SCAN_ROWS);
```

这样可以直接扫描：

```text
ROW_TICKS = 1400
ROW_TICKS = 1350
ROW_TICKS = 1320
ROW_TICKS = 1300
ROW_TICKS = 1280
```

逐步逼近上限。实际场刷新率为：

```text
实际刷新率 = 50 MHz / (ROW_TICKS × 32)
```

## 肉眼判断最高刷新率的局限

单靠肉眼不能精确测出 500 Hz、800 Hz 或 1200 Hz。肉眼可以判断：

- 是否闪烁
- 是否出现拖影
- 是否发生撕裂
- 是否有随机错误
- 亮度是否明显下降

但不能可靠区分：

```text
800 Hz 和 1000 Hz
```

更可靠的辅助方法是：

1. 用示波器测 `hub_lat`，每 32 个 LAT 周期为一帧；
2. 增加一个 `frame_mark` 输出，每完成一帧翻转一次；
3. 测量 `frame_mark` 周期；
4. 用高速摄像机拍摄屏幕，观察滚动条纹和扫描断层。

`frame_mark` 逻辑应放在最后一个地址完成的位置：

```verilog
if (row_count == SCAN_ROWS-1) begin
    row_count  <= 0;
    anim_phase <= anim_phase + 7'd1;
    frame_mark <= ~frame_mark;
end
```

测量关系是：

```text
场刷新率 = 2 / frame_mark 的完整周期
```

因为 `frame_mark` 每完成一帧只翻转一次。

## 建议的最终测试顺序

1. 使用黑白 1 像素竖条，固定 `FRAME_HZ=120`，测 `hub_clk` 上限。
2. 在稳定的最高 `hub_clk` 下，逐步减小 `ROW_TICKS`。
3. 使用彩色竖条检查 RGB 通道。
4. 使用行地址诊断图检查 A~E。
5. 用移动亮点观察是否撕裂和丢帧。
6. 用示波器测量 `frame_mark`，记录实际场刷新率。
7. 对最后一个稳定点运行至少 10 分钟。

最终建议记录两个值：

```text
最高稳定 HUB75 CLK：例如 8.33 MHz
最高稳定整屏刷新率：例如 600 Hz
```

这两个值才是系统设计中有意义的参数。 fpga-docs 的 MIZAR-Z7 手册确认了板上 PL 时钟为 50 MHz、JP1/JP2 默认 I/O 电压为 3.3 V，因此当前工程的时钟粒度和 I/O 电平设置都应以这两个条件为基础。

在每个目标帧率下，屏幕应满足：

- 从左到右始终是细密的红、绿、蓝竖条；
- 颜色顺序稳定；
- 白色标记线连续移动；
- 上半屏和下半屏完全一致；
- 没有随机闪点；
- 没有整屏颜色突然变化；
- 没有局部区域变黑；
- 没有左右错位；
- 没有明显鬼影或拖尾。

### 像素 CLK 或刷新率过高时的异常

如果超过屏幕或当前时序的稳定范围，通常会出现：

- RGB 条纹变成杂色；
- 竖条顺序错乱；
- 屏幕左右出现不连续；
- 上下半屏内容不一致；
- 局部列随机闪烁；
- 白色标记线变成多根；
- 画面出现斜向、横向或块状异常；
- 亮度突然下降；
- 某些扫描行不显示。

其中，**颜色错乱、条纹错位、白线分裂和局部黑行**比肉眼判断移动速度更有价值，它们说明扫描时序或面板接收能力已经出现问题。

## 正确的测试方式

需要把“帧率测量”和“肉眼观察”分开。

### 1. 用示波器测真实帧率

增加一个 `frame_mark` 输出，每完成一帧就翻转一次：

```verilog
output reg frame_mark;
```

复位时：

```verilog
frame_mark <= 1'b0;
```

最后一个扫描地址完成时：

```verilog
if (row_count == SCAN_ROWS-1) begin
    row_count  <= 0;
    anim_phase <= anim_phase + 7'd1;
    frame_mark <= ~frame_mark;
end else begin
    row_count <= row_count + 1'b1;
end
```

示波器测量 `frame_mark` 的周期：

```text
真实帧率 = 2 / frame_mark 周期
```

例如：

```text
frame_mark 周期 = 2 ms
帧率 = 2 / 2 ms = 1000 Hz
```

因为 `frame_mark` 每帧只翻转一次，所以一个完整方波周期包含两帧。

### 2. 用逻辑分析仪测 `LAT`

每个 `LAT` 脉冲对应一个扫描地址：

```text
地址扫描频率 = LAT 频率
整屏帧率 = LAT 频率 / 32
```

例如测到：

```text
LAT = 32 kHz
```

则：

```text
帧率 = 32 kHz / 32 = 1000 Hz
```

### 3. 肉眼只判断画面质量

肉眼测试图不应再用“每帧移动一像素”来测速度，因为高刷新率下移动太快。它只用于判断画面是否正常：

- RGB 细条纹是否持续稳定；
- 白色标记线是否分裂；
- 是否出现随机闪点；
- 是否有整行或局部黑屏；
- 是否出现左右错位；
- 上下半屏是否一致；
- 亮度是否明显下降；
- 是否出现鬼影。

达到最高刷新率附近时，最容易观察的不是运动速度，而是**图像错误和亮度变化**。

## 推荐增加“慢速可视化监视”

保留真实刷新率不变，但让白色标记线每隔固定帧数移动一次。例如：

```verilog
parameter integer MARK_DIV = 120;
```

在每帧结束时：

```verilog
if (mark_count == MARK_DIV-1) begin
    mark_count <= 0;
    anim_phase <= anim_phase + 7'd1;
end else begin
    mark_count <= mark_count + 1'b1;
end
```

这样：

```text
实际帧率：1000 Hz
MARK_DIV：1000
白线每秒移动 1 像素
```

显示扫描仍然是 1000 Hz，但白线移动速度被降低到肉眼可观察范围。注意这只是观察辅助，不能用白线移动速度反推帧率，真实帧率仍应使用 `frame_mark` 或 `LAT` 测量。

更实用的测试图是：

```text
固定 RGB 细竖条 + 慢速移动白色标记线
```

其中：

- RGB 细竖条用于发现像素 CLK/移位错误；
- 白色标记线用于观察是否卡顿、撕裂或跳变；
- 示波器 `frame_mark` 用于测真实帧率。

## 推荐最终测试流程

1. 固定 `PIXEL_CLK_HZ=5 MHz`，逐步提高 `TARGET_FRAME_HZ`。
2. 使用示波器测 `frame_mark`，记录实际帧率。
3. 肉眼观察 RGB 条纹是否错误、亮度是否下降、是否鬼影。
4. 出现错误后退回一个档位。
5. 在最高稳定点连续运行 10 分钟。
6. 再提高 `PIXEL_CLK_HZ`，重复测试。

你最终需要记录的不是“肉眼看到的帧率”，而是：

```text
实际 frame_mark 测得的帧率
屏幕可接受的最高 HUB75 CLK
最高稳定显示帧率
最高稳定显示时的亮度和图像质量
```

因此，2000 Hz 即使理论上可以实现，也应该通过 `frame_mark` 或 `LAT` 的电信号测量，而不是通过肉眼判断。
